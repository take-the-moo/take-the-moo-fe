## 3. 작업 시작 절차

1. 요청을 한 문장으로 정리하고 F1~F7 중 관련 기능과 완료 조건을 정한다. 문서 작업이면 문서 자체가 완료 대상이다.
2. `git status --short`와 관련 diff로 기존 변경을 확인한다. 다른 사람의 수정·미추적 파일·환경 파일을 정리하거나 덮어쓰지 않는다.
3. `rg`로 대상의 정의·호출부·타입·목·설정을 함께 찾는다. 추측한 파일 구조나 존재하지 않는 API에 맞추어 구현하지 않는다.
4. Next.js 코드 변경이면 아래 설치 버전의 관련 문서를 읽는다. 프레임워크를 변경하면 해당 규칙도 다시 확인한다.
5. 디자인 작업이면 전체 페이지 링크에서 대상 프레임을 특정한다. 메타데이터는 구조 확인용이며 픽셀 검증 근거가 아니다.
6. 불명확한 계약을 표시하고, 독립적으로 진행 가능한 작업부터 수행한다. 요청하지 않은 가입·새 플랫폼·AI 기능을 추가하지 않는다.

경로는 프로젝트 루트 기준이다. 의존성 설치 후 열 수 있으며, 설치 버전의 문서가 일반적인 기억보다 우선한다.

## 4. 구현 경계 규칙

### API·목

- 공통 요청은 `src/api/client.ts`를 사용한다. 호출 경로에 `/api`를 중복해서 넣지 않는다.
- 공통 응답의 `data` 추출과 `ApiError` 처리를 페이지마다 복제하지 않는다.
- 사진 업로드는 합의된 `FormData` 계약을 따른다. multipart `Content-Type` 경계를 직접 만들지 않는다.
- 새 엔드포인트를 목 모드에서도 사용한다면 `src/mocks/handlers.ts`를 함께 갱신한다. 지원하지 않는 요청을 임의의 성공 응답으로 처리하지 않는다.
- 실제 필드·에러 코드를 백엔드와 확인한다. 타입 단언이나 고정 목만으로 계약이 맞는다고 판정하지 않는다.
- F6 후기 저장의 422 같은 도메인 실패를 화면에 설명하고 입력을 유지한다. 네트워크 실패와 성공을 구분한다.

### 상태·언어

- 익명 사용자 ID·국적·언어는 기존 `useUserStore`의 책임이다. 새 저장소를 중복하지 않는다.
- 서버 조회·캐시는 기존 QueryClient 기반을 활용한다. 서버 데이터를 localStorage에 임의로 복제하지 않는다.
- 일시적인 입력·로딩·오류는 화면 상태로 둔다. 초기화 시 사용자 정보와 화면 상태의 범위를 구분한다.
- UI 문구는 `src/i18n/index.ts`, 생성 콘텐츠 번역은 API 책임이다. 국적과 표시 언어를 같은 값으로 가정하지 않는다.
- 사용자가 국적·언어·장소를 바꿨을 때 이전 조건의 응답이 새 화면을 덮지 않도록 요청과 캐시 키를 구분한다.

### 지도·기기

- 위치·카메라·알림·공유는 `src/platform/`에서 플랫폼 차이를 처리한다.
- `loadNaverMaps()` 완료 후 지도·파노라마를 사용한다. 임의 스크립트 주입으로 기존 로더를 우회하지 않는다.
- `[lng, lat]`와 `(lat, lng)` 변환은 `toLatLng()`를 사용한다. 검증용 근사 좌표를 실제 코스 데이터로 확정하지 않는다.
- 리스너·지도 인스턴스·비동기 작업은 화면 종료와 Fast Refresh를 고려해 정리한다.
- 위치 권한 거부·조회 시간 초과·카메라 취소·지도 인증 실패를 각각 확인한다. 웹 알림 함수의 무동작을 네이티브 알림 성공으로 보고하지 않는다.
- 앱 진입·복귀 시 단발성 위치 조회를 사용한다. 지속 추적·백그라운드 위치 수집을 MVP에 추가하지 않는다.

### 환경·배포

- pnpm과 `package.json`의 `packageManager` 버전을 사용한다. 다른 패키지 관리자의 잠금 파일을 추가하지 않는다.
- 기존 `.env.local`을 덮어쓰지 않는다. 문서·예시는 `.env.example`의 자리표시자만 사용한다. 실제 비밀값을 로그·diff·문서에 옮기지 않는다.
- `NEXT_PUBLIC_*`는 공개·빌드 시 반영되는 값이다. AI·외부 서비스 비밀키를 프런트엔드에 넣지 않는다.
- 지도 키는 Maps Application Client ID와 등록 URL을 확인한다. 계정 Access Key를 대체값으로 사용하지 않는다.
- iOS 개발 서버 모드와 출시용 정적 번들을 구분한다. `CAP_ENV=bundle` 지정만으로 현재 Next.js 서버 프록시가 대체되지 않는다.
- 정적 export 전환 시 rewrites 미지원, 동적 경로, 실제 API 주소·접속 정책을 함께 검토한다.

AI·개인정보 규칙은 프런트엔드 검사만으로 보장되지 않는다. 후보 제한·번역 전용 처리·후기 필터·위치 비저장은 서버 계약과 해당 서버의 검증 증거도 필요하다. 민감한 역사 표현은 요구서의 기억·평화 원칙을 지키고, 시연 언어는 사람이 검수한다.

요구서의 위치 거부 대체 경로와 Figma의 분기 제거, 익명 시작과 선택 가입·취향 설정은 미해결 차이다. 구현 작업의 완료 조건에 영향을 주면 사용자에게 확인하고 결정 근거를 남긴다.

## 6. 검증 단계와 실행 기준

현재 저장소에는 `test` 스크립트·전용 테스트 파일·CI 워크플로가 없다. 아래 명령과 수동 검증은 운영 절차이며, 자동으로 실행되는 게이트라고 표현하지 않는다.

| 변경 종류 | 필요한 검증 |
| --- | --- |
| 문서만 변경 | 소스·요구서 대조, 링크·경로·코드 블록 확인, diff 공백 검사 |
| TypeScript·화면 로직 | 관련 결함의 재현·수정 확인, lint·타입 검사, 변경 화면의 로딩·실패·빈 상태 확인 |
| API·목 | 목과 실서버 각각의 계약·오류·업로드 확인. 미접속 환경은 별도로 기록 |
| 지도·기기 | `/dev/map-check`와 관련 화면, 권한 허용·거부, 웹·iOS별 실제 동작 확인 |
| 설정·라우팅·배포 | lint·타입·빌드, 실제 사용 모드로 실행. 번들이면 산출물·라우팅·API 확인 |

일반 코드 변경에 사용하는 정적 검사:

```bash
pnpm lint
pnpm exec tsc --noEmit --incremental false
```

빌드·배포 동작을 바꾸면 추가 실행:

```bash
pnpm build
```

`next/font/google`의 폰트 다운로드처럼 외부 네트워크가 필요한 단계에서 실패하면 환경 원인과 코드 원인을 분리한다. 실패한 빌드를 성공으로 기록하지 않는다. 타입 검사에서 생성된 Next.js 타입이 필요하면 생성 상태를 확인한다.

비자명한 분기·오류 처리를 추가하면 재현 가능한 작은 검증을 남긴다. 이미 있는 도구와 수동 재현으로 충분한 변경에 새 테스트 프레임워크를 도입하지 않는다. 자동화가 필요하면 범위를 별도 합의한다.

### 수동 확인 순서

1. **목 모드**: `/`에서 API 호출 결과의 `mock: true` 확인. 현재 목 범위는 health·사용자 생성 두 개임을 전제로 한다.
2. **실서버 모드**: `NEXT_PUBLIC_USE_MOCK=false`와 백엔드 주소를 설정하고 서버 재시작 후 같은 요청의 실제 응답을 확인한다.
3. **지도**: 등록 URL·키를 설정한 뒤 `/dev/map-check`에서 지도·선·마커·거리뷰 상태와 인증 오류를 확인한다.
4. **위치**: 허용·거부·시간 초과를 확인한다. 현재 홈에는 거부 로그만 있고 역 선택 화면은 없다.
5. **iOS**: 개발 서버를 실행하고 `pnpm ios`로 확인한다. 알림 테스트는 예약·표시·탭을 구분한다. 탭하면 `/scene/{placeId}`(04 장면)로 이동한다. 장면 내용은 아직 샘플이다.
6. **시연**: 위치·날씨 시뮬레이션과 엽서 사전 생성·백업 영상은 요구서상 준비 항목이다. 아직 구현되거나 준비되었다고 가정하지 않는다. 샘플 기록은 샘플임을 밝힌다.

## 7. 실패 시 피드백 루프

1. 실행 모드·경로·입력·기대 결과·실제 결과를 기록한다. 비밀키·개인 좌표·개인 사진은 증거에서 제외한다.
2. 실패를 UI, API, 목, SDK 인증, 권한, 네이티브, 환경으로 좁힌다. 재현 없이 관련 없는 설정을 바꾸지 않는다.
3. 공통 책임이 있는 가장 좁은 계층에서 수정한다. 증상을 가리는 고정 성공 응답을 추가하지 않는다.
4. 실패했던 시나리오와 영향을 받는 경계를 다시 확인한다. 통과 후 근거 없이 검증 범위를 계속 늘리지 않는다.
5. 같은 실수가 반복되면 해당 모듈의 설명·검증 절차에 재발 방지 항목을 추가한다. 일회성 로그를 영구 지침으로 쌓지 않는다.

## 8. 완료 조건과 인계

- 요청 범위가 충족되고 관련 호출부·타입·목·설정이 일치한다.
- 기존 사용자 변경과 환경값이 보존되었다.
- 필요한 검증 결과가 기록되었다. 미검증 항목은 완료했다고 표현하지 않는다.
- 화면·API·실행 방법이 바뀌면 아키텍처와 관련 문서를 갱신했다.
- 요구서·디자인 차이는 결정 또는 미확정 상태로 남아 있다.

완료 보고에는 다음 내용을 간결하게 남긴다.

```text
변경: 해결한 요구사항과 변경 파일
근거: 요구서 기능 번호 / Figma 프레임 / 관련 코드·가이드
검증: 실행한 명령·환경·결과
미검증·제약: 접속하지 못한 서버·기기, 미확정 계약
다음 작업: 남은 항목이 있을 때만 기재
```

이 문서를 유지하기 위해 루트 `AGENTS.md`를 대체하거나 실행 코드·CI·비밀 설정을 추가할 필요는 없다. 의존성·스크립트·화면 구현 상태가 바뀌면 해당 설명도 함께 갱신한다.
